## Timeouts and region

Before the user's region change, Vercel reported `iad1`, Virginia, while the paid Neon database was in Singapore. A direct database probe from this machine measured 1.20 seconds for the first connection and 82 to 83 ms for warm `SELECT 1` calls. Two rounds of seven actual API reads took 1.65 to 8.88 seconds. All returned 200. No sampled request exceeded the app's 12-second read-attempt deadline, so the reported timeout was not reproduced by this probe.

The user set Vercel's project region to Mumbai, `bom1`. The repository configuration now also specifies `"regions": ["bom1"]` in `apps/api/vercel.json`. The new serving deployment, `dpl_BaX5trDHMw6LR1qKop6dXpqydeqb`, uses source `f4b760785a81dcd07d9283ceb977467e70a9150f` and reports `bom1` in its deployment metadata. Authenticated responses also contain `bom1::bom1` region traces, confirming that the function itself runs in Mumbai. The deployment immediately before this one still ran in `iad1` despite the changed project setting. [Vercel's region documentation](https://vercel.com/docs/functions/configuring-functions/region) explains the effect of function/database distance and permits a single chosen region on Hobby.

The same seven read paths were measured again after deployment, twice each in parallel rounds. All returned 200; none crossed the app's 12-second read-attempt deadline. Their durations ranged from 0.76 to 3.86 seconds. Mean overview time fell from 7.67 to 3.03 seconds, traveler-list time from 2.86 to 1.62 seconds, and checklist time from 3.64 to 2.20 seconds. Itinerary time changed from 1.65 to 1.78 seconds. These are small samples from one disposable trip, not a load test or proof that every reported timeout is fixed. The later checklist contained three small test entries; the earlier one was empty. Timings include HTTP, authentication and SQL work.

The API uses Drizzle with a node-postgres pool of five connections per process, a 10-second connection-acquisition deadline and 30-second idle cleanup. The app bounds each Query read attempt at 12 seconds and retries a transient read once. Several database operations and Clerk user/session verification happen within a single API request. An API deadline therefore does not prove that the database itself timed out. Do not raise every timeout or remove authorization checks to conceal that distinction.

The new bulk-delete operation uses a fixed set of database queries in one transaction. It does not issue a separate network request and transaction for each selected record.

## Changes to consider

1. Keep the current paid Neon endpoint and data. Mumbai is now verified on the serving deployment, and the repeated reads passed. No database account or capacity change is indicated by these samples. If timeouts recur, capture the failing route and server request ID before changing a provider tier.
2. Choose which R2 account should own the files. Keep the live bucket until a deliberate migration is ready. To move it, copy existing objects with their exact keys and metadata, verify hashes and private access, account for uploads during cutover, then change `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` together in the API's intended environments and local configuration. Redeploy the API. R2 credentials are server-only, so this cutover does not require an Android rebuild. Retain the original bucket for rollback until references and reads have been checked.
3. R2 is metered storage with a free allowance and usage charges. A Cloudflare website Pro plan is not an R2 performance tier. Do not buy a website-plan upgrade to address SQL delays. See [R2 pricing](https://developers.cloudflare.com/r2/pricing/).
4. If a different paid Vercel team should own the API, transfer the existing project only after identifying that team. Preserve its environment values, domains, root directory, Mumbai region and deployment settings. No team transfer is needed merely to select one function region.
5. Upgrading the current Clerk application's billing can preserve its existing instance. Switching from development to production or to another Clerk app is a separate identity migration. Change API `CLERK_SECRET_KEY` and `CLERK_PUBLISHABLE_KEY` and Android `EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY` together, complete domain/OAuth/native registration, and plan the existing `members.clerk_user_id` mappings. A fresh Clerk instance does not automatically retain trip membership. No auth migration was performed.
6. The live Production environment has `CRON_SECRET` but no `EXPO_ACCESS_TOKEN`. The local API environment contains both. The Expo server token is optional and is consumed by remote notification dispatch. Its absence affects remote push, not ordinary database reads. Configure it securely if remote delivery is required, then redeploy and test delivery.

Vercel stores the server variables as sensitive values and does not return their plaintext through the environment-list API. The audit therefore used live database correlation, accepted Clerk identity and signed file-authorization metadata to identify the active services. Empty values in that metadata response are redaction, not missing runtime configuration.

No plan upgrades, database moves, R2 copies, account transfers or production-auth changes were made during the audit.
